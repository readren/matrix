# Architectural Decision Record: Generic Out-of-Line ByteSource Serialization

**Status:** Accepted

## Context

The cluster transport ([Cluster Binary Serialization](cluster-serialization.md)) transfers every message as a framed package accumulated in a per-connection circular direct-buffer ring (`DualEndedCircularStorage`) bounded by a configurable capacity ceiling (by default 128 buffers of 8 KB, or 1 MB).

Consensus `InstallSnapshot` messages ([Lazy Raft Consensus Protocol Specification](lazy-multi-raft-consensus.md)) embed state machine snapshots (`SnapshotByteSource`) whose size is unbounded. Streaming these payloads inline through `Serializer.Writer` and `Deserializer.Reader` creates two symmetrical bottlenecks:

1. **Reception:** `Receiver` accumulates all frames of a package in `DualEndedCircularStorage` before invoking `Deserializer.deserialize`, failing with `BuffersCountExceededException` once the total package size exceeds the circular buffer ceiling.
2. **Transmission:** `Transmitter` runs `Serializer.serialize` synchronously on the caller thread (the consensus `sequencer`). Because reading and serializing bytes into memory outpaces socket transmission, the caller exhausts `DualEndedCircularStorage.advanceWriteEnd()` before network writes drain the ring, aborting the package with `CORRUPTED_PACKAGE_SENTINEL`. Blocking during serialization is impossible because it would freeze the single-threaded `sequencer`.

At the same time, forcing `Serializer` and `Deserializer` (and the TASTy macro derivation engine) into an asynchronous continuation-passing style or manually splitting domain messages (`InstallSnapshot`, `SnapshotData`) into separate control envelopes and transport-specific stream calls would pollute protocol definitions and higher-level bridge logic.

## Options Considered

### Bulk Serialization and Streaming Architecture

1. **Virtual-thread pipelined de-accumulation.** Run `Deserializer.deserialize` on a virtual thread concurrently with socket reception. Rejected: it does not solve the synchronous transmitter overrun on the caller thread without asynchronous serializer continuations, and materializing snapshots into contiguous heap arrays (`IArray[Byte]`) causes severe garbage-collection pressure.
2. **Application-level control envelope plus manual transport streaming API.** Split `InstallSnapshot` in `ClusterWireProtocol` into an envelope message and invoke dedicated `transmitWithStream` / `receiveTrailingStream` methods in `Nio2ClusterBridgeCdm`. Rejected: leaks streaming mechanics into protocol schemas and bridge dispatchers, cannot handle `ByteSource` values nested inside arbitrary composite types automatically, and duplicates framing concepts.
3. **Generic `ByteSource` trait in `common` with Deferred Out-of-Line Queueing in `Serializer.Writer` / `Deserializer.Reader` and Eager Pre-Delivery in `Receiver`.** Selected.

### Pipelined Stream Leftover Management Options

When a single socket read delivers the final chunk sentinel of a trailing stream together with unconsumed bytes belonging to a subsequent message, the transport receiver must transfer those leftover bytes from the streaming subsystem into the message framing subsystem without corrupting message framing or allocating excessive memory.

1. **Direct in-place multi-buffer slicing across circular storage.** Slice unconsumed leftover bytes from `streamTransferBuffer` across one or more buffers in `DualEndedCircularStorage` during trailing stream finalization. Rejected: `DualEndedCircularStorage` uses smaller, independently bounded direct buffers (e.g., 8 KiB), whereas `streamTransferBuffer` is sized for high-throughput streaming (e.g., 64 KiB). Pipelined bytes can easily exceed the remaining capacity of the current buffer or span multiple circular buffers. Slicing raw bytes across the ring during stream finalization requires manually allocating buffers, calculating split frame headers, and tracking buffer limits outside the normal framing state machine. This breaks the uniform contract of the asynchronous read completion callback and introduces high defect surface.
2. **Direct slice retention inside `streamTransferBuffer`.** Retain unconsumed bytes in `streamTransferBuffer` and point subsequent message framing reads directly into that buffer. Rejected: buffer reuse collision hazard. If the subsequent pipelined message also contains a trailing stream (or transitions into stream mode), `streamTransferBuffer` is immediately cleared and reused for socket reads. A network read into `streamTransferBuffer` would physically clobber the unconsumed message bytes currently being read by circular storage, resulting in silent memory corruption or deserialization failures.
3. **Layered buffering asynchronous channel wrapper.** Wrap `AsynchronousSocketChannel` in a general-purpose buffered channel decorator that handles stream and framing reads transparently. Rejected: introduces unnecessary object allocation on every connection, adds extra layers of asynchronous completion indirection, and decouples buffering from the specific framing lifecycle of `Receiver`.
4. **Isolated heap staging with virtualized channel interception (`streamTransferLeftover` + `readChannel`).** Selected. Copy unconsumed leftover bytes from `streamTransferBuffer` into an isolated heap buffer (`streamTransferLeftover`) and reset circular storage's target buffer to empty. All subsequent circular storage reads are routed through `readChannel`, which intercepts read requests to feed from `streamTransferLeftover` via the standard completion callback before falling back to physical socket reads.

## Decision

### 1. Foundational `ByteSource` Abstraction in `common`

- A reusable `ByteSource` trait is defined in `common` (`readren.common.ByteSource`), representing a size-known, repeatable supplier of binary streams. It exposes `def size: Long`, `def openAsyncReader(): ByteSource.AsyncReader`, `def openChannel(): java.nio.channels.ReadableByteChannel`, and `def transferTo(target: java.nio.channels.WritableByteChannel): Long`.
- Polymorphic asynchronous I/O is supported through `ByteSource.AsyncReader` (`def read[A](dst: ByteBuffer, attachment: A, handler: CompletionHandler[Integer, ? >: A]): Int`) returning non-negative synchronous bytes read, `-1` on immediate EOF, or `ByteSource.AsyncReader.PENDING = -2` when completing asynchronously via `handler`, and staging sinks through `ByteSink` (`def write[A](src: ByteBuffer, attachment: A, handler: CompletionHandler[Integer, ? >: A]): Int` returning synchronous bytes written or `ByteSink.PENDING = -1`, `def seal(): Unit`, `def asByteSource: ByteSource`, `def discard(): Unit`).
- Staging allocation is abstracted by `ByteSink.Allocator` (`def allocate(expectedSize: Long): ByteSink`). The default allocator (`ByteSink.DefaultAllocator`) stages payloads smaller than or equal to a configurable threshold (by default 64 KiB, or size 0) in memory via `BufferByteSink` / `BufferByteSource`, and stages larger payloads in temporary files via `FileByteSink` / `FileByteSource` backed by `AsynchronousFileChannel`. Backing temporary files employ a hybrid lifecycle: explicit `close()` deletes the file immediately, while an internal `java.lang.ref.Cleaner` safety-net cleans unlinked files upon garbage collection.
- In `consensus/core`, `SnapshotByteSource` aliases or extends `readren.common.ByteSource`.

### 2. Deferred Out-of-Line Queueing in `Serializer.Writer` and `Deserializer.Reader`

- `Serializer.Writer` exposes `putByteSource(source: ByteSource): Unit` and `Deserializer.Reader` exposes `readByteSource(): ByteSource`, backed by standard given instances `Serializer[ByteSource]` and `Deserializer[ByteSource]` in `CommonSerializers`.
- **Synchronous tree traversal is preserved:**
  - When `PipelinedTransmitter`'s serialization writer (or `Transmitter`'s writer) handles `putByteSource(source)`, it writes only the unsigned VLQ byte length (`source.size`) at the current inline position in the control package and appends `source` to its outbound stream queue. Synchronous serialization of the remaining message fields (such as trailing log batches after a snapshot) completes immediately in memory.
  - When `Receiver`'s reader handles `readByteSource()`, it reads the inline unsigned VLQ byte length, allocates a staging `ByteSink` via the configured `ByteSink.Allocator`, appends the staging sink and expected byte count to an internal `pendingByteSinks` queue, and immediately returns a deferred `ByteSource` handle so the enclosing message finishes constructing synchronously.
- Standalone in-memory `Writer` and `Reader` implementations (used outside `Transmitter`/`Receiver` in unit tests) default to writing and reading the payload bytes inline after the VLQ length.

### 3. Wire Framing (`STREAM_FOLLOWS_SENTINEL`)

- A control package whose `pendingByteSources` queue is empty terminates with the standard `0x00` sentinel.
- A control package whose `pendingByteSources` queue is non-empty terminates with a reserved sentinel `STREAM_FOLLOWS_SENTINEL` (`0xffff_fffd`, `-3` in 32-bit two's complement), followed immediately by a single concatenated trailing stream covering all queued payloads in FIFO order.
- The trailing stream consists of length-prefixed chunks (`VLQ32(n > 0)` followed by `n` raw bytes) terminated by either `0x00` (uncorrupted completion) or `CORRUPTED_PACKAGE_SENTINEL` (`0xffff_fffe`, in-band abort).
- **Self-delimitation invariant:** The wire stream remains parseable without schema knowledge; any receiver can drain and discard a trailing stream by reading chunk length headers until `0x00` or `0xffff_fffe`.
- **In-band abort and selective teardown invariant:** If reading a queued `ByteSource` fails or yields fewer bytes than its declared `size`, `PipelinedTransmitter` (or `Transmitter`) emits `CORRUPTED_PACKAGE_SENTINEL` at the current chunk boundary, reports `ByteSourceProblem`, and keeps the connection open while draining any queued messages. On the inbound path, when `Receiver` encounters a clean in-band `CORRUPTED_PACKAGE_SENTINEL` at a chunk boundary without prior control deserialization faults or local sink errors, it discards the partial staging sinks, keeps the socket channel open, and immediately restarts reception for subsequent messages. Any mid-stream framing defect, declared size mismatch, draining control fault, or local sink I/O failure on `Receiver` immediately closes the socket channel and unlinks all staging files.
- **Length conservation invariant:** The total bytes across all chunks of an uncorrupted trailing stream must equal the sum of the inline `size` values declared by the queued `ByteSource`s in the control package; any discrepancy is a fatal framing fault.

### 4. Constant-Memory Streaming and Eager Pre-Delivery

- **PipelinedTransmitter / Transmitter:** After flushing the control package and `STREAM_FOLLOWS_SENTINEL` during the transmission stage, `PipelinedTransmitter` streams each queued `ByteSource` asynchronously using `ByteSource.AsyncReader` into the network socket channel via a lazily allocated direct transfer buffer (configurable per channel, defaulting to 64 KiB, and released upon returning to idle). Synchronous completions from in-memory readers are handled immediately via direct return status (`readStatus != ByteSource.AsyncReader.PENDING`), avoiding trampoline recursion, while concurrent outbound transmissions queue cleanly in `PipelinedTransmitter` and are pre-serialized in the serialization stage without blocking callers. (The single-flight `Transmitter` maintains its active-transmission guard throughout control transmission and trailing streaming to reject concurrent calls.)
- **Receiver (Eager Pre-Delivery):** Upon encountering `STREAM_FOLLOWS_SENTINEL`, `Receiver` deserializes the control package (populating `pendingByteSources` with allocated `ByteSink` instances) and immediately transitions into asynchronous stream mode before invoking `onComplete`. It streams incoming chunks into each queued staging sink in FIFO order without advancing `DualEndedCircularStorage`, maintaining $O(1)$ direct memory. Synchronous staging writes execute inline (`writeStatus != ByteSink.PENDING`) without trampoline flags. Chunk lengths are validated strictly (continuation shifts `< 28`, non-negative, and bounded by expected total stream bytes); any protocol violation, peer abort, or channel I/O failure immediately tears down the socket channel and discards staging files.
- **Deferred Sink Sealing:** `Receiver` defers calling `sink.seal()` until the final asynchronous file write completes, preventing premature channel closure (`AsynchronousCloseException`). Only after all staging sinks are sealed and the trailing `0x00` terminator is verified does `Receiver` deliver the deserialized message to `onComplete`.
- **Clean Peer Abort Recovery vs. Mid-Stream Fatal Teardown:** A clean in-band `CORRUPTED_PACKAGE_SENTINEL` emitted mid-stream by a sender unlinks partial staging files via `sink.discard()` and skips the aborted package while keeping the socket channel open for pipelined follow-up messages. Conversely, local staging sink I/O failures, draining control deserialization faults, VLQ chunk headers exceeding 5 bytes (32 bits), or declared size mismatches immediately close the underlying socket channel, unlink staging files, and deliver a `Receiver.Fault`.

### 5. `ByteSource` Ownership and Lifecycle in Consensus

- **Active workspace ownership:** `Workspace` owns the `SnapshotByteSource` referenced by `workspace.latestSnapshot`. Neither `Storage.save` nor `StateMachine.installSnapshot` closes the active snapshot payload.
- **Replacement and release:** When `Workspace.truncatePrefix` or `Workspace.resetLog` replaces an existing snapshot with a different `SnapshotByteSource` instance, or when `Workspace.release()` is invoked, the superseded `SnapshotByteSource` is closed.
- **Rejection cleanup:** When `onInstallSnapshot` completes without adopting the received snapshot into `Workspace` (e.g., stale term, leader role, or batch-only log fusion), the participant closes the rejected `SnapshotByteSource` immediately so its temporary staging file is deleted.

### 6. Trailing Stream Leftover Pipelining and Channel Virtualization

To seamlessly transition between constant-memory stream mode and framed message reception when TCP packets deliver bytes across stream boundaries, `Receiver` implements isolated leftover staging and virtualized channel read interception:

- **Case 1 (Leftover in `streamTransferBuffer` or Prior Staged Leftovers Remaining):** When the trailing stream reads beyond the initial packet into `streamTransferBuffer` (or when unconsumed bytes from an earlier stream remain in `streamTransferLeftover`), any unconsumed bytes in the active stream source followed by any remaining bytes in `streamTransferLeftover` belong to subsequent messages. Slicing them across circular storage directly or leaving them in `streamTransferBuffer` is prohibited. `Receiver` concatenates those unconsumed bytes in chronological order into an isolated heap buffer (`streamTransferLeftover`) and resets `circularStorage.writeEnd` to empty with its initial limit.
- **Case 2 (Leftover in `circularStorage.writeEnd` with Empty Staged Leftovers):** When the entire trailing stream was contained within the initial circular storage buffer and `streamTransferLeftover` is empty, no reads were issued to `streamTransferBuffer`. In this case, `Receiver` shifts unconsumed pipelined bytes in-place via `target.compact()` without heap allocation, sets `streamTransferLeftover = null`, and subsequent `receiveWithAttachment` calls immediately trigger the completion handler with 0 bytes when `writeEndBuffer.position > 0` to parse already buffered bytes without network I/O.
- **Channel Virtualization via `readChannel` Across Both Framing and Streaming Reads:** All reads targeting either circular storage buffers or `streamTransferBuffer` are routed through `readChannel`. If `streamTransferLeftover` is non-null and has remaining bytes, `readChannel` copies available bytes into the destination buffer and dispatches `handler.completed` directly, simulating a channel read. Once `streamTransferLeftover` is completely drained, it is dereferenced for immediate garbage collection, and subsequent reads pass through directly to `channel.read`.
- **Rationale for Chosen Architecture:**
  1. *Elimination of Buffer Reuse Clobbering Hazards:* Isolating leftover bytes in an independent buffer decouples downstream message framing from stream buffer recycling. If the subsequent message also has a trailing stream, `streamTransferBuffer` can be cleared and used for socket reads without risk of clobbering unconsumed data.
  2. *Preservation of Framing and Streaming Continuity:* Feeding staged bytes through `readChannel` for both control framing and trailing stream chunk reads ensures that pipelined bursts containing consecutive streaming messages consume staged bytes strictly in chronological order without bypassing buffered data or hanging on empty sockets.
  3. *Zero-Allocation Fast Path:* In non-pipelined flows or when the stream was fully absorbed in the initial buffer with no prior staged leftovers (Case 2), zero heap allocations occur. When pipelining across stream boundaries does occur, allocating a transient heap buffer in young-generation Eden space (typically tens or hundreds of bytes) incurs negligible GC overhead compared to socket I/O latency, while providing absolute safety against memory corruption.
  4. *Idle Buffer Pruning Safety:* Circular storage is pruned down to `minBuffersOnIdle` only when both `circularStorage.writeEnd.position == 0` and `streamTransferLeftover == null`, ensuring that idle buffer reclamation never discards pipelined message bytes waiting in staging.

## Invariants

- **Asynchronous Non-Blocking ByteSource I/O Invariant:** Reading and writing bulk payloads across transport channels must use non-blocking asynchronous interfaces (`ByteSource.AsyncReader` and `ByteSink`). Dedicated thread blocking during payload transfer is strictly prohibited.
- **Atomic Work-Stealing Stream Trampoline Invariant:** Both outbound trailing stream transmission (`PipelinedTransmitter`) and inbound trailing stream ingestion (`Receiver`) serialize all state transitions across synchronous return values, inline completion callbacks (invoked before `read` or `write` returns `PENDING`), and multi-threaded asynchronous completion callbacks using an atomic work-stealing permit counter, guaranteeing $O(1)$ stack depth, single-owner mutual exclusion, zero lost wakeups, and at-most-once stream finalization. Without this trampoline, direct looping callers would have to require `ByteSource.AsyncReader` and `ByteSink` never to invoke `CompletionHandler` inline before returning `PENDING` (reporting synchronous results solely via their `Int` return value), avoid unbounded inline leftover reads, and rely on `AsynchronousSocketChannel` bounding consecutive inline callback depth.
- **Allocator Staging Threshold Invariant:** The transport receiver delegates payload buffer management to `ByteSink.Allocator`. Payloads below or equal to the staging threshold (64 KiB) are staged in memory with zero file system touches; payloads exceeding the threshold are staged in temporary disk files using asynchronous I/O.
- **Deferred Sink Sealing and Rollback Unlinking Invariant:** In `Receiver`, calling `sink.seal()` on a `ByteSink` must occur strictly after the final asynchronous write completion for that sink has executed, and any staging sinks already sealed during a multi-stream message must still be discarded and unlinked if a subsequent stream in the same package aborts or faults prior to message completion.
- **Buffer Identity Compaction Invariant:** When a trailing stream finishes within the initial buffer where `leftoverSource` and `circularStorage.writeEnd` reference the identical `ByteBuffer` and no prior staged leftovers remain, `target.compact()` must be called instead of `target.put(leftoverSource)` to eliminate self-put exceptions (`src == this`).
- **Multi-Buffer Deserializer Boundary Catch-Up Invariant:** When a control package's serialized payload exactly exhausts the current circular storage buffer and the package terminator sentinel resides at the start of the subsequent buffer, `Receiver` must catch up `readEndBuffer` to `writeEndBuffer` prior to verifying complete consumption of the package, preventing false positive `TheDeserializerHasNotConsumedTheWholePackage` reception faults.
- **Split Frame Header Limit Invariant:** When an incoming frame header spans across buffer boundaries (`SPLIT`), the buffer limit must be extended to `nextFrameHeaderPos + FRAME_HEADER_MAX_SIZE` (using the reserved capacity), guaranteeing that the full maximum header width can be accommodated without clamping or truncating previously received bytes.
- **Trailing Stream Leftover Staging and Channel Virtualization Invariant:** Unconsumed pipelined bytes following a trailing stream must be staged in chronological order into an isolated leftover buffer and fed through `Receiver`'s virtualized channel read interceptor for both subsequent circular storage framing reads and subsequent trailing stream chunk reads, preventing cross-stream memory clobbering, bypassed leftover bytes, and socket read hangs on pipelined bursts.
- **Unsigned Wire Sentinel Decoding Invariant:** Transport control sentinels (`CORRUPTED_PACKAGE_SENTINEL = 0xffff_fffeL`, `STREAM_FOLLOWS_SENTINEL = 0xffff_fffdL`) are defined as unsigned 32-bit values represented as positive 64-bit `Long` constants ($2^{32}-2$, $2^{32}-3$). `Receiver` decodes frame lengths via `VLQ.tryToDecodeUnsignedInt` as non-negative 64-bit unsigned `Long` values, cleanly distinguishing valid frames and in-band stream sentinels from buffer exhaustion (`-1L`) and package terminations (`0L`) without signed integer promotion discrepancies.

## Consequences

- **Total protocol and bridge transparency:** `ClusterWireProtocol`, `SnapshotData`, `Transmitter.transmit`, `SequentialTransmitter.transmit`, and `Receiver.receive` retain their exact existing types and signatures. Any message type containing zero, one, or multiple `ByteSource` fields at any nesting depth is streamed automatically.
- **Constant memory and zero heap copies:** Bulk payloads bypass `DualEndedCircularStorage` and heap arrays on both sides, using a single reusable direct buffer per direction and streaming between disk and socket.
- **Head-of-line blocking with overlapping serialization preparation on shared connection:** While a trailing stream is in flight in the transmission stage of a peer connection, subsequent messages submitted concurrently queue safely in `PipelinedTransmitter` (with the next message pre-serialized in the serialization stage) and wait for the active stream to finish on the wire. In heartbeat-less Lazy Raft, this cannot cause spurious elections.
- **Evolution to shared elastic buffer pooling and consensus concurrency governance:** While static per-channel streaming buffers provide strict $O(1)$ direct memory bounds per connection, scaling to hundreds of concurrent connections motivates migrating from per-instance transfer buffers to an elastic direct buffer pool in `nexus/cluster` paired with an application-level snapshot concurrency governor in `consensus/core`. Capping pool retention to $K$ idle buffers while allowing unbounded on-demand allocation prevents socket deadlocks and TCP ZeroWindow stalls, while consensus-level admission control prevents physical disk and network thrashing.
